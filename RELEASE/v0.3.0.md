# v0.3.0 — Operability: config, auth, push/pull ingestion

Status: **Not started.**

## Planned scope

- Single YAML config file (`config.yaml`) with feature flags for every optional subsystem (see [DESIGN/08](../DESIGN/08_design_config_auth_ops.md) §8.1).
- `circa config init` (with `--profile minimal`/`--profile full` and targeted overrides).
- `circa config check <file>` — schema + cross-field validation before a restart.
- `/status` page rendering the effective merged config, secrets redacted.
- No-auth default, matching node_exporter/Prometheus; multi-user, bcrypt-hashed basic auth when `auth.users` is non-empty (see [DESIGN/08](../DESIGN/08_design_config_auth_ops.md) §8.2).
- `circa auth add-user <name>` / `circa auth reset-password <name>` (local/SSH-run, no self-service reset — see §8.2.2 for why).
- `/api/v1/write` receiver: Prometheus remote-write wire format (protobuf + Snappy), feature-flagged (`push.receive`) (see [DESIGN/04](../DESIGN/04_design_collection_and_ingestion.md) §4.2).
- Outbound push sender to an external remote-write endpoint, feature-flagged (`push.send`). Both default off; pull-based scraping remains the zero-config default.

## Why this is next

Before adding intelligence (alerting/anomaly detection) or remote/export features, Circa needs to be deployable and securable in production, and needs its ingestion surface fully rounded out (pull scrape from v0.1.0, plus push receive/send here).
