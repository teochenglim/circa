# v0.3.0 — Operability: config, auth, push/pull ingestion

Status: **Shipped.**

## Planned scope

- Single YAML config file (`config.yaml`) with feature flags for every optional subsystem (see [DESIGN/08](../DESIGN/08_design_config_auth_ops.md) §8.1).
- `circa config init` (with `--profile minimal`/`--profile full` and targeted overrides).
- `circa config check <file>` — schema + cross-field validation before a restart.
- `/status` page rendering the effective merged config, secrets redacted.
- No-auth default, matching node_exporter/Prometheus; multi-user, bcrypt-hashed basic auth when `auth.users` is non-empty (see [DESIGN/08](../DESIGN/08_design_config_auth_ops.md) §8.2).
- `circa auth add-user <name>` / `circa auth reset-password <name>` (local/SSH-run, no self-service reset — see §8.2.2 for why).
- `/api/v1/write` receiver: Prometheus remote-write wire format (protobuf + Snappy), feature-flagged (`push.receive`) (see [DESIGN/04](../DESIGN/04_design_collection_and_ingestion.md) §4.2).
- Outbound push sender to an external remote-write endpoint, feature-flagged (`push.send`). Both default off; pull-based scraping remains the zero-config default.

## Why this is next

Before adding intelligence (alerting/anomaly detection) or remote/export features, Circa needs to be deployable and securable in production, and needs its ingestion surface fully rounded out (pull scrape from v0.1.0, plus push receive/send here).

## Built

Shipped as planned, with a few implementation notes worth recording:

- **Config validation** (`internal/config/config.go`): `Config` now decodes `alerting`/`backup`/`push`/`auth` in full (alerting's `rules`/`notifiers` stay loosely typed as `yaml.Node` — their real schema is v0.4.0's to design). A new `Validate() []error` runs every cross-field check from DESIGN/08 §8.1.2's example (`backup.mode` pull-without-catalog-URI, `push_send` on without a URL, an `auth.users` value that doesn't look like a bcrypt hash, etc.) and reports *all* problems in one pass, not just the first. `Load` now calls `Validate` and fails startup on a bad config instead of surfacing broken state later.
- **`circa config init`/`check`** (`cmd/circa/config_cli.go`, `internal/config/template.go`): `init` renders a fully-commented YAML template via `text/template` (not `yaml.Marshal`, which would drop every comment) with `--profile minimal|full` plus `--hostname`/`--listen`/`--retention.*` overrides; refuses to overwrite an existing file. `check <file>` is a thin wrapper around `Load`+`Validate` that requires the file to actually exist (unlike normal startup, where a missing `-config` path means "use defaults").
- **`circa auth add-user`/`reset-password`/`hash-password`** (`cmd/circa/auth_cli.go`, `internal/auth/userfile.go`): `add-user`/`reset-password` prompt twice for a password (`golang.org/x/term.ReadPassword`, no echo), bcrypt-hash it, and upsert `auth.users.<name>` into the config file by editing the parsed `yaml.Node` tree in place — comments and formatting elsewhere in the file survive, unlike a full struct round-trip. `add-user` refuses to overwrite an existing user; `reset-password` refuses to create a new one. `hash-password` (added after initial review — there was no way to just get a hash without pointing the CLI at a specific file) prompts the same way but only prints the bcrypt hash to stdout, touching no file, for hand-editing config.yaml or generating hashes in CI. Flag parsing for `add-user`/`reset-password` is order-independent (`-config` may appear before or after the username) since `flag.FlagSet` stops parsing at the first positional argument, which would otherwise make `circa auth add-user admin -config x.yaml` silently fail.
- **Basic auth** (`internal/auth/auth.go`): `Middleware` wraps a handler with HTTP Basic Auth checked against `auth.users` (bcrypt); an empty/nil map disables auth entirely (the default). A missing username still runs `bcrypt.CompareHashAndPassword` against a fixed dummy hash so failed-auth latency doesn't leak which usernames exist — the dummy hash is generated once at package load (`bcrypt.GenerateFromPassword` on a fixed string) rather than a hardcoded hash literal, since a literal bcrypt-hash-shaped string in source trips Semgrep's `detected-bcrypt-hash` secret-scanner rule even though it's never a real credential. `httpapi.NewRouter` wraps everything *except* `/healthz`/`/readyz` in this middleware — liveness/readiness probes shouldn't need credentials.
- **`GET /status`** (`internal/httpapi/httpapi.go`): renders the effective, merged `Config` as YAML via `Config.Redacted()` (bcrypt hashes replaced with `[redacted]`). `config.Duration` gained a `MarshalYAML` so retention/interval fields render as `"1h0m0s"` instead of raw nanosecond counts — without it, `/status` output was unreadable.
- **`/api/v1/write` receiver** (`internal/ingest/remotewrite/receiver.go`): decodes a Snappy-compressed `prompb.WriteRequest` body and feeds each sample into the same `ingest.Pipeline` scraped/future-influx samples use — no separate code path downstream of decode. Uses `github.com/prometheus/prometheus/prompb` directly (plus `github.com/golang/snappy`) rather than hand-rolling a protobuf decoder, matching DESIGN/04 §4.4.1's "same libraries Prometheus itself uses." Received samples get a fixed 15s interval (the true source-side scrape interval isn't recoverable from the wire format) — reasonable default, not a guarantee.
- **Push sender** (`internal/ingest/remotewrite/sender.go`): a `Sender` ticks on `push.send.interval`, and on each tick walks every series `internal/query.Engine.Series()` knows about, queries raw points since that series' last-sent watermark, and pushes them (protobuf+Snappy) to `push.send.url`. **Watermarks are in-memory only, not persisted** — a restart re-sends up to one interval's worth of overlap, which the receiving side's storage simply overwrites (last-write-wins on identical timestamps). Acceptable for v0.3.0; revisit if exactly-once delivery ever matters here, or fold into the watermark mechanism v0.5.0's backup CDC export will need anyway.
- **New dependencies**: `github.com/prometheus/prometheus/prompb` (+ transitively `github.com/gogo/protobuf`, `github.com/grafana/regexp`), `github.com/golang/snappy`, `golang.org/x/crypto/bcrypt`, `golang.org/x/term`. All are either generated wire-format types or single-purpose stdlib-adjacent packages — no new architectural dependency (no TSDB, no service discovery) despite `prometheus/prometheus` being the module path. Pinned to `github.com/prometheus/prometheus` **v0.313.1**, not the first version that satisfied the API (v0.55.1) — that older line carries two HIGH CVEs (Azure OAuth secret disclosure via the config API, remote-read DoS via uncontrolled allocation) in subsystems this package never imports, but `trivy fs` scans `go.mod` at the module level and can't do reachability analysis, so an older pin would fail `pre-commit`'s `trivy-fs` hook regardless of actual exposure.

**Deferred, as planned:** alert rule engine, anomaly detection, backup/federation, `/metrics` exposition (all explicitly v0.4.0/v0.5.0 per DESIGN/09 §9.2), and config hot-reload on `SIGHUP` (DESIGN/08 §8.1.3 mentions it; not implemented — every config change currently requires a restart). **Also not built, but worth flagging:** the InfluxDB line-protocol receiver (`internal/ingest/influx`) — `ingest.influx.path` config/validation landed here (since `config.example.yaml` already had the field) but the actual `/write` handler doesn't exist yet. It was never actually in v0.3.0's planned scope (see this file's own "Planned scope" above) or assigned to any later milestone in DESIGN/09 §9.2 either — worth deciding where it lands before `features.influx_receive` gets turned on anywhere.

**Verified beyond unit tests:** full suite green (`go vet`/`go test -race -cover`, 62 tests across 10 packages incl. new `internal/auth`, `internal/ingest/remotewrite`, `cmd/circa` CLI tests). Ran the actual `circa` binary end-to-end: `config init --profile minimal|full` followed by `config check` on both outputs; a deliberately broken config (`push_send: true` with no URL) correctly rejected with a clear error; `auth add-user` against a running config file, confirmed the bcrypt hash round-trips and a second `add-user` for the same name is rejected; started a real server with `auth.users` set and confirmed `/status` 401s without credentials, 200s with correct ones (and 401s with wrong ones), while `/healthz` stayed open; pushed a real Snappy+protobuf remote-write payload via a throwaway Go program and confirmed the sample showed up in `/api/v1/query_range`; ran two `circa` instances end-to-end (a "sender" with `push_send`+`push_receive` both on, and a "receiver" with just `push_receive` on) and confirmed a sample pushed into the sender's own `/api/v1/write` was forwarded by its `push.send` goroutine and became queryable on the receiver — the full round-trip DESIGN/04 §4.4.2 describes.
