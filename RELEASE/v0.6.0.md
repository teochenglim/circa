# v0.6.0 — Netdata-style dashboard: zero-config system overview

Status: **Shipped.**

## Planned scope

- Redesign `web/` around a Netdata-like local-agent layout for the metrics v0.5.0's built-in collector now produces automatically: a top-level system overview (CPU, memory, network, disk, load) rendered the moment Circa starts against an empty `config.yaml` — no scrape target, no manual chart configuration. Use the local `netdata/` clone as the visual/interaction reference (chart grouping, dense multi-chart grid, live auto-updating panes), not as code to copy wholesale — Circa keeps its existing uPlot-based rendering (see [DESIGN/05](../DESIGN/05_design_ui.md)), it's the information architecture and layout conventions being matched, not Netdata's stack.
- Auto-generated chart groups keyed off the fixed collector categories from v0.5.0 (`cpu`, `memory`, `network`, `disk`, `filesystem`, `load`) rather than v0.2.0's per-scrape-target/per-measurement grouping — that grouping stays as-is for externally scraped/pushed sources (postgres_exporter, custom apps, etc.), this is a second, zero-config-specific view layered alongside it, not a replacement.
- "Nodes" affordance stays singular/local — per [ARCHITECTURE.md](../ARCHITECTURE.md) "Deployment shape" and [DESIGN/05](../DESIGN/05_design_ui.md)'s existing "per-node local dashboard, not a multi-tenant/multi-host view" decision, this is *not* the start of a Netdata Cloud-style fleet view; each Circa instance still only ever renders its own node's data.
- Existing Alerts and "what's unusual" panels (v0.4.0) stay as-is, positioned alongside the new overview rather than rebuilt — this milestone is about the default/landing view, not a rewrite of everything shipped in v0.2.0–v0.4.0.
- Verify with the Playwright-based pattern already used for v0.4.0's panels (see servicedesk's `CLAUDE.md` for the pattern to copy, and this repo's own [CLAUDE.md](../CLAUDE.md) note that `curl`/unit tests don't execute client-side JS) — screenshot light and dark, against a real server with only v0.5.0's local collector enabled and no scrape targets configured, to prove the zero-config claim actually holds.

## Why this is next

Directly depends on [v0.5.0](v0.5.0.md) shipping first — there's no "zero-config system overview" to build a UI for until the local collector exists and is flowing samples through the normal ingest pipeline. Sequenced before [v0.7.0](v0.7.0.md) (federation/self-expose) since a good local, zero-config default view is more central to a first-run experience than exposing data to other systems.

## Built

Shipped, with one deliberate departure from the planned scope: real per-category **pages** (own URL, own `<title>`, own route) rather than one page with JS-toggled sections. The plan above described a single dense-grid landing page; mid-implementation feedback was that Netdata's actual UI is tab-per-page (Overall / CPU / Memory / ...), and that's a materially better fit — each page loads only the JS/data it needs, each is bookmarkable, and it avoids a client-side tab-state machine entirely. The compact Overall grid described in the plan still exists, it's just one tab among eight now instead of the whole dashboard.

- **Eight pages, one shared nav** (`web/template/*.html`, `web/template/nav.html`'s `{{define "nav"}}` block, `web/embed.go`'s `pages` route map): `/` (Overall — the compact 6-chart grid the original plan described), `/cpu`, `/memory`, `/network`, `/disk`, `/filesystem`, `/load` (one detail page per v0.5.0 collector category), and `/metrics` (the pre-existing manual metric-picker chart + Alerts/"what's unusual" panels, relocated here unchanged — "stays as-is" from the plan, just moved to its own page instead of sharing the landing page).
- **Overall vs. detail pages, deliberately different scope, not duplicated views**: Overall shows one aggregate/primary line per category (CPU: overall busy%; Network: primary-route interface only, via `node_network_primary_info`; Disk: summed across devices; Filesystem: `/` only) for an at-a-glance read. Each detail page shows the full breakdown the plan's "auto-generated chart groups" called for — every CPU core, every network interface (including secondary/USB adapters — the reason `node_network_primary_info` and per-device breakdowns were both built), every disk device, every mounted filesystem, every collected memory series in raw bytes.
- **`internal/collect`'s v0.5.0 output drives all of it with zero manual chart config**, as planned: `web/static/js/circa-data.js` (new, shared fetch/rate/merge math), `overview.js` (Overall page), `detail.js` (the six category pages) all discover series via `GET /api/v1/series` and build charts from whatever `node_*` metrics actually exist — nothing hardcoded to a specific OS's metric set, both Linux's and macOS's deliberately-different vocabularies (see RELEASE/v0.5.0.md) are handled.
- **Grafana-style legend interaction** (not in the original plan, added after early feedback that plain uPlot legends don't isolate a series on click): `web/static/js/circa-chart.js`'s `legend: {isolate: true}` turns on a click behavior **uPlot already has natively** — no custom logic needed, just switching it on (confirmed by reading uPlot's actual legend-click source, not assumed). What uPlot doesn't provide — clicking empty chart area to restore every series — is a small custom listener on `plot.over`. Applied uniformly to every chart on every page via the shared `CircaChart`/`CircaData` modules.
- **A real design pass** (also not in the original plan — first pass looked like generic Bootstrap-blue-and-gray, correctly called out as far from "Netdata look and feel"): `web/static/css/app.css` was rebuilt around the project's own existing but previously-unused brand mark (`images/favicon.svg`'s teal ring-and-sparkline, `#2dd4bf`/`#0f766e`) instead of ad hoc hex codes — a named category-color system (`--cat-cpu`, `--cat-memory`, ...) applied consistently to a card's border, its detail page's heading bar, and its chart's line color (via `circa-data.js`'s `categoryColor()`, which reads the same CSS custom properties), a warm-neutral palette instead of stark white/pure-black, uppercase eyebrow-style card titles, and a small pulsing "live" indicator by the wordmark (respects `prefers-reduced-motion`). The favicon itself was also never actually wired up before this — `web/static/img/favicon.svg` + a `<link rel="icon">` on every page fixes that too.
- **Verified with Playwright as planned**, against a real server with only `features.collect` on and no scrape targets (proving the zero-config claim), light and dark, across all eight pages: every chart container confirmed to contain a real rendered `<canvas>` (not just "the page returned 200"), zero browser console/page errors across all sixteen page×theme combinations, and the legend isolate/click-to-restore interaction verified by asserting on uPlot's actual `u-off` CSS class before/after clicking, not just visually eyeballing a screenshot. One real bug caught and fixed during this pass: a 3-series merge (`mergeOnX` folding in `node_load5` after `node_load1`, then `node_load15`) only re-aligned the newest series onto the widened x-axis and silently left the earlier ones desynced — fixed by having `mergeOnX` re-align every existing y-series on each fold, not just the incoming one (see its doc comment).

**Deliberately deferred**: per-device disk I/O and full host-filesystem visibility from inside a container remain v0.5.0's known gaps (unaffected by this milestone); a "nodes" fleet-view affordance stays out of scope per the plan's own note.
