# v0.7.0 — Federation & self-expose: backup, federation search, `/metrics`

Status: **Shipped.**

## Planned scope

- Watermark-driven delta export, Arrow record batches written as Parquet, appended to an Iceberg table (see [DESIGN/07](../DESIGN/07_design_backup.md)).
- Both push mode (each node exports directly) and pull mode (`/api/v1/backup_range` + a central backup agent) — see §7.3 for the tradeoff. Feature-flagged (`features.backup`), default off.
- Confirm cross-node queries work with plain SQL (DuckDB locally, or Trino/Spark for larger fleets) against the shared Iceberg table, filtered by `node_id` (see [DESIGN/07](../DESIGN/07_design_backup.md) §7.5). No new component to build here — this is verification that the table schema/partitioning from the backup work above actually supports it, not new code.
- Wire up `/metrics` in Prometheus exposition format, fed by whatever's been scraped/ingested/collected (see [DESIGN/04](../DESIGN/04_design_collection_and_ingestion.md) §4.2) — lets Circa itself be scraped or federated from an existing Prometheus.

## Why this is last

This milestone is entirely about Circa's data leaving the node — to a shared Iceberg lake, to a federated query engine, or to another scraper polling `/metrics`. Deliberately sequenced after storage, UI, compression, config/auth, ingestion, alerting, anomaly detection, built-in system collection, and the Netdata-style dashboard are all in place, since every one of those is more central to Circa's own value than exposing/re-exporting its data to something else.

## Built

Shipped as planned, plus one substantial addition (full RED self-metrics across every subsystem, not just `/metrics` itself) that emerged from mid-implementation feedback, and two real bugs found and fixed along the way.

- **`internal/backup`** — the full CDC mechanism from DESIGN/07 §7.2-§7.4:
  - `delta.go`'s `CollectDelta` reads every series' tier-1 (minute-rollup) points after a watermark, shared identically by push mode (`LocalSource`, calling it in-process) and pull mode (the `GET /api/v1/backup_range` handler, calling it to serve a remote `Exporter`) — DESIGN/07 §7.3's "only real difference is which side initiates the Iceberg write."
  - `watermark.go`'s `WatermarkStore` persists a single global watermark to a local JSON file (not per-series — DESIGN/07 §7.2 floated per-series/per-shard, but one sweep across every series per run is simpler and sufficient at this scale), advanced only after the Iceberg commit succeeds.
  - `iceberg.go`'s `IcebergWriter` builds an Arrow record from a batch of rows and calls `Table.AppendTable` — **the official `apache/iceberg-go` v0.6.0 directly**, not the community fork DESIGN/07 originally pointed to (that fork was written off as necessary before checking; by v0.6.0 the official module already had real `Append`/`AppendTable` support, confirmed by reading the actual source, not the README's summary). Schema is DESIGN/07 §7.4's sketch minus `env`/`region` (nothing populates them) and with `labels` as a JSON string column, not a native map column (simpler to build, equally queryable) — see [DESIGN/07](../DESIGN/07_design_backup.md) §7.4 for the full reasoning.
  - `exporter.go`'s `Exporter` runs on a real cron schedule (`github.com/robfig/cron/v3`, standard 5-field syntax) — config.example.yaml already had `schedule: "*/15 * * * *"` in cron syntax since the config-decode-only era, so this actually parses it rather than reinterpreting it as a duration.
  - **Push mode**: wired into `cmd/circa/main.go` — on `features.backup && backup.mode == "push"`, connects to the catalog at startup (failing loudly if unreachable, per this repo's "bad config fails at startup" convention — DESIGN/07 §7.6's outage-resilience story is about a *transient* mid-run failure, not a wrong URI at boot) and runs the exporter against a `LocalSource`.
  - **Pull mode**: `internal/httpapi`'s `GET /api/v1/backup_range?since=<unix_ts>` (only registered when `mode: pull`) serves a node's own delta; `circa backup-agent -config <file>` (`cmd/circa/backup_cli.go`, a new subcommand alongside `config`/`auth`) is the central poller — one `Exporter` per `backup.nodes` entry, each with its own watermark file, sharing one `IcebergWriter`/catalog connection. A `backup-agent` config is expected to be a *separate* file from a polled node's own config (the agent's has real catalog credentials + `backup.nodes`; a polled node's just needs `mode: pull` to serve the endpoint, never touching Iceberg itself).
  - Credentials: `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` env vars (the AWS SDK's own default chain, not a config field) plus optional `CIRCA_BACKUP_CATALOG_TOKEN` for REST catalog bearer auth — DESIGN/07 §7.6's "config-light" credentials story.
- **`GET /metrics`** (`internal/httpapi/metrics.go`) — Prometheus exposition format via `prometheus/common/expfmt`, built differently than DESIGN/09 §9.1's original sketch of "written to the standard Prometheus registry on every ingest": instead, it reads lazily on each scrape — the latest point per series straight out of `internal/storage` via `internal/query`, over a 5-minute lookback window (generous relative to the 15s scrape/collect default). Simpler: no second in-memory copy of "current value per series" to keep in sync with storage.
- **Self-metrics — RED (rate/errors/duration) across every subsystem, not just HTTP** (not in the original plan; added after feedback that "each component deserves good RED metrics," not just the API surface). Every package registers its own via `promauto` into the shared `prometheus.DefaultRegisterer` — see [ARCHITECTURE.md](../ARCHITECTURE.md)'s new "Self-metrics" section for the full table of what's tracked in `internal/httpapi`, `internal/storage`, `internal/ingest/scrape`, `internal/ingest/remotewrite`, `internal/collect`, `internal/alert`, and `internal/anomaly`, plus `internal/backup` itself. `GET /metrics` gathers from `prometheus.DefaultGatherer`, so this needed zero wiring change in `httpapi` beyond the initial self-metrics — every package's own `metrics.go` shows up automatically. This is DESIGN/05's previously-unspecified "lightweight self-metrics panel" — the metrics exist and are scrapeable now; a dashboard **page** rendering them is deferred to [RELEASE/v1.0.0.md](v1.0.0.md)'s final UI polish pass.
- **Federation search verified for real** (DESIGN/07 §7.5) — not just asserted: a live Iceberg REST catalog (`apache/iceberg-rest-fixture`) + MinIO stood up via Docker, `internal/backup` wrote real rows through the actual production code path (not a scratch/mock harness), and a real DuckDB query (`iceberg_scan` against the S3-backed table) read them straight back, including `json_extract` against the `labels_json` column — confirming cross-node federation really is "just a SQL query," not an aspiration.
- **Two real bugs found and fixed, not just new code written**:
  1. `config.Validate()`'s backup checks had catalog requirements backwards since the config-decode-only era: `backup.catalog.uri` was required only for `mode: pull` and `backup.catalog.warehouse` was required unconditionally — exactly inverted from reality (only `push` mode writes to Iceberg from this process; a `pull`-mode node just serves `backup_range` and never touches the catalog). Fixed to require both fields only for `mode: push`.
  2. `helm/circa/templates/secret.yaml` and `k8s/11-secret.example.yaml` dumped backup credentials as `BACKUP_S3_ACCESS_KEY`/`BACKUP_S3_SECRET_KEY` env vars — names `internal/backup` never actually reads (it uses the AWS SDK's standard `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`). Since `envFrom: secretRef` passes a Secret's keys through verbatim with no renaming, push-mode backup deployed via either manifest would have silently failed to authenticate to S3. Fixed both, added `CIRCA_BACKUP_CATALOG_TOKEN`, and removed an unrelated dead `AUTH_USERS_YAML` field in the same k8s secret example that never wired to anything either (`internal/auth` reads `auth.users` from the config file, not an env var).
- **Tests**: unit tests for `WatermarkStore` (load/save round-trip, missing-file-is-zero-time) and `CollectDelta` (exclusive lower bound, watermark advancement) against a real `storage.TieredStore`; a Docker-gated integration test (`CIRCA_TEST_ICEBERG_URI` env var) exercising `IcebergWriter.Append`/read-back against the same live catalog used for the DuckDB verification above — skipped by default (no such infrastructure in a normal `go test ./...` environment), with the exact `docker run` commands to stand it up in the test's own doc comment; `internal/httpapi` tests for `/metrics` and `/api/v1/backup_range` (route registration gated correctly on `features.backup`/`backup.mode`, delta content correctness).

**Deliberately deferred**: exactly-once export semantics (a crash-and-retry re-exports the same window; DESIGN/07 §7.2 flagged upsert mode as the fix if this ever matters, not built); Iceberg snapshot expiry/compaction (explicitly a lake-maintenance concern per §7.6, not Circa's job); a dashboard page for self-metrics (v1.0.0).
