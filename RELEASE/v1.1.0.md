# v1.1.0 — Windows (and other non-Linux/non-macOS) system collection

Status: **Not started.**

## Planned scope (see [DESIGN/09](../DESIGN/09_design_tech_stack_and_roadmap.md) §9.2)

- Extend [v0.5.0](v0.5.0.md)'s built-in `internal/collect/` collector to Windows, behind its own build tag (`_windows.go`, matching the `_linux.go`/`_darwin.go` split from v0.5.0) — same core metric set (`cpu`, `meminfo`, `diskstats`, `filesystem`, `netdev`, `loadavg`-equivalent), same `ingest.Sample` normalization, same feature-flagged `collect` config section.
- Windows has no `/proc`/`sysctl` equivalent — the mechanism is WMI (Windows Management Instrumentation) via `golang.org/x/sys/windows` or a WMI client library, not a filesystem-parsing port of the Linux/macOS work.
- Reference `windows_exporter` (WMI-based, MIT-licensed — a separate codebase and license from node_exporter/netdata) under the same reuse policy v0.5.0 established: read for coverage/edge cases, never import or vendor. Same rationale — avoid framework coupling (its collectors are wired into its own CLI/registration machinery too) and keep `internal/collect/` in one consistent, from-scratch style across every platform it supports.
- Evaluate other non-Linux/non-macOS targets (*BSD, etc.) at the same time if there's real demand by then; not committed scope until that demand exists.

## Why this is after v1.0.0

v1.0.0 is a hardening/packaging pass over what v0.1.0–v0.7.0 already ship (sizing calculator, systemd/Docker/Helm packaging, docs) — it isn't the vehicle for adding new platform coverage. Windows support is real, wanted work, but it's additive scope, not a hardening task, so it's sequenced as its own milestone after the 1.0 line rather than folded into either v1.0.0 or v0.5.0 (whose primary dev/test loop is Linux + macOS, per v0.5.0's own "Why this is next").
