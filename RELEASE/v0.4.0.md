# v0.4.0 — Intelligence: alerting + anomaly detection

Status: **Shipped.**

## Planned scope

- Rule engine: metric selector + condition (threshold/rate-of-change/anomaly-bit) + hysteresis + severity (see [DESIGN/06](../DESIGN/06_design_alerting_and_anomaly_detection.md) §6.1).
- Webhook + Slack incoming-webhook notifiers behind a pluggable dispatch interface.
- Alerts view in the UI. Feature-flagged (`features.alerts`), default off.
- Per-metric k-means (k=2) ensemble, starting with 3–5 models per metric on staggered training windows (see [DESIGN/06](../DESIGN/06_design_alerting_and_anomaly_detection.md) §6.2).
- Anomaly bit embedded in the existing storage format (no separate time series).
- "What's unusual right now" ranked view in the UI. Feature-flagged (`features.ml`), default off — document rough CPU/RAM cost per 1,000 metrics before shipping.

## Why this is next

Alerting and anomaly detection both act on the storage/query foundation from v0.1.0–v0.3.0 and share the same "feature-flagged, default off" shape — grouping them keeps the rule-engine-to-anomaly-bit wiring (threshold conditions can reference the anomaly bit) as one milestone instead of a half-finished dependency across two.

## Built

Shipped, with the anomaly-detection half implemented against **Netdata's actual C++ source** (a real local clone under `netdata/`, gitignored, kept for reference — see [DESIGN/10_ml_summary.md](../DESIGN/10_ml_summary.md)), not just DESIGN/06 §6.2's paraphrase of it. That doc is the canonical mapping of what's replicated vs. deferred; this section summarizes what shipped.

- **Alert rule engine** (`internal/alert/`): `Rule` = metric selector (name + exact-match labels) + `Condition` (`ThresholdCondition`, `RateOfChangeCondition`, `AnomalyCondition`) + `For` (hysteresis) + `Severity`. **`For` is duration-based** ("must hold continuously for at least this long"), matching Prometheus's own `for:` clause — a deliberate reinterpretation of DESIGN/06 §6.1's "N evaluations" phrasing, since evaluation cadence varies per scrape target's interval and a wall-clock duration is both more portable and a convention users already know. `Engine` implements `ingest.Consumer` and evaluates every rule against each sample on the same tick as ingestion (§6.1's own requirement), tracking hysteresis/firing state per (rule, series) pair and dispatching a firing *and* a resolved notification on each state transition (not just firing — a small addition beyond the design doc that makes the feature meaningfully more usable).
- **Notifiers** (`internal/alert/notify/`): `Webhook` (generic JSON POST) and `Slack` (incoming-webhook, formatted one-line message). Both implement `alert.Notifier`; new channels are a new file in this package per ARCHITECTURE.md's existing guidance, untouched by this work.
- **`GET /api/v1/alerts`**: every currently-firing alert. Returns an empty list (not 404) when `features.alerts` is off, so the UI never special-cases the flag.
- **Anomaly bit storage** (`internal/storage/anomalybit.go`): `EncodeAnomalyBit`/`DecodeAnomalyBit` steal the LSB of the stored float64 (Netdata's own trick, per §6.2) — `Store.Append` gained an `anomalous bool` parameter, `Point` gained an `Anomalous` field. Rollup (`#min`/`#avg`/`#max`) points are always `anomalous=false` — a bucket average has no single anomaly verdict of its own.
- **k-means(k=2) anomaly detection** (`internal/anomaly/`) — matched line-for-line in intent against `ml_kmeans.cc`/`ml_features.cc`/`ml_config.cc`:
  - **Preprocessing** (`Preprocess`): difference (order `DiffN`, default 1) → smooth (rolling mean, `SmoothN`, default 3) → lag (`LagN`, default 5, giving 6-value feature vectors) — same order, same math as `ml_features.cc`.
  - **Scoring** (`Model.Score`): mean Euclidean distance to *both* centroids (not nearest-centroid), min-max normalized against the min/max of that same metric observed during training, into `[0,100]`. Degenerate case handled exactly like Netdata: `MinDist == MaxDist` (a perfectly constant training set) scores `0` always — "nothing to compare to," not "everything is anomalous," which a naive percentile-threshold approach (this package's first draft, since replaced) gets wrong.
  - **Ensemble** (`Detector`): up to `ModelCount` (default **18**, matching Netdata's `number of models per dimension`) models per series, accumulated via **FIFO** — each `RetrainInterval`, one freshly-trained model is appended and the oldest evicted once at capacity, so the ensemble ends up holding models trained at genuinely different points in time, not `ModelCount` copies of "trained on the same recent window" (an earlier round-robin-overwrite draft got this wrong; see DESIGN/10_ml_summary.md §3). A point counts as anomalous only if **every** currently-trained model agrees (`ml.cc`'s own short-circuit: the first model scoring below threshold vetoes the whole check).
  - **Staggering**: series are fanned out across `RetrainInterval` in 12 sub-ticks rather than all retraining at once — simpler than Netdata's shared worker-pool queue-pacing, suited to a single Go process, same goal (spread CPU cost).
  - **Wiring** (`cmd/circa/main.go`): `Detector.Score` runs *before* `ingest.Pipeline.Ingest`, not as a fanned-out `Consumer` — the anomaly bit has to be known before `internal/storage` embeds it into the value it writes, and before `internal/alert`'s `AnomalyCondition` can read it off `ingest.Sample.Anomalous`.
- **`query.Engine.AnomalyRanking`**: per-series anomaly rate over a recent window (default 10 minutes, `?window=<seconds>` overridable), ranked highest-first, omitting series with zero anomalous points — DESIGN/06 §6.2's "ranked list... rather than forcing per-metric inspection," computed by reading the anomaly bit already in raw storage, no new aggregation subsystem. Exposed as `GET /api/v1/anomalies`.
- **Dashboard UI** (`web/`): an Alerts panel and a "What's unusual" panel, both polling their endpoints on the existing 15s auto-refresh timer, both present but empty when their feature is off. Verified against real rendered output (Playwright screenshot, light and dark), not just `curl`/unit tests — pushed real threshold-breaching and anomalous samples through a live server and confirmed both panels render correctly, per this repo's own rule that `curl`-only checks don't cover client-side JS.
- **Config** (`internal/config/config.go`): `Alerting.Rules`/`Notifiers` and `Anomaly` are now fully typed (previously `[]yaml.Node` placeholders). `Config.Validate` gained `validateAlerting`/`validateAnomaly` — unknown condition/notifier types, an `anomaly` condition rule with `features.ml` off, a notifier name a rule references but never defines, `anomaly.*` bounds mirroring Netdata's own clamp ranges. `Config.Redacted` now also masks notifier webhook URLs (they routinely embed a bearer token, e.g. Slack's incoming-webhook path) alongside the bcrypt hashes already redacted in v0.3.0. `circa config init --profile full` now generates a real example rule/notifier instead of empty lists.
- **New dependency**: none — `internal/anomaly`'s k-means is entirely from-scratch (per DESIGN/06 §6.2's own recommendation: "a from-scratch implementation is realistic and avoids a heavy dependency").

**Deliberately deferred** (see DESIGN/10_ml_summary.md §3 for the full Netdata-mechanism-by-mechanism comparison): per-dimension suppression/silencing of a perpetually-noisy series, the constant-metric training shortcut, `hosts/charts to skip` scope filters, model persistence across restarts (ensembles are in-memory only — a restart starts cold), the `max_training_vectors` sampling cap for very fine-grained series, and a single host-wide anomaly-rate threshold event (the ranked list serves the same triage purpose for a single-node dashboard). PagerDuty-Events-API and email notifiers (DESIGN/06 §6.1 mentions them as a "next" addition beyond webhook/Slack) aren't built — webhook already covers PagerDuty's own generic webhook ingestion path as a workaround. Alertmanager-compatible payload format (§6.1's "consider supporting") also isn't built.

**Rough cost, measured, not guessed** (per the planned scope's own "document rough CPU/RAM cost per 1,000 metrics before shipping"): training one k-means(k=2) model at Netdata's default settings (6h window, 15s scrape interval → ~1440 raw points, 500 iterations, 6-value feature vectors) took **~11ms** on the machine this was measured on (`internal/anomaly.Train`, single-threaded, no special hardware). At 1,000 metrics with the default 18-model ensemble and 3h retrain interval, the 12-way staggered fan-out means roughly 83 series retrain every 15 minutes (`RetrainInterval`/12) — about **0.9s of CPU work every 15 minutes**, not a burst. Memory per trained model is tiny (~106 bytes: two 6-value centroids plus min/max distance), so 1,000 metrics × 18 models is under 2MB of model state. The one caveat this benchmark surfaced: training *every* series back-to-back in a single batch (rather than the actual staggered schedule) at Netdata's own upper iteration bound (1000) is measurably slow at scale (didn't finish 1,000 series in 120s) — which is exactly why the staggered fan-out design, not a batch retrain loop, is the right shape here; `maxIterations` (currently 500, matching Netdata's own default) has real headroom to tune down if CPU ever becomes a constraint, since k=2 converges in far fewer iterations in practice.

**Verified beyond unit tests:** full suite green (`go vet`/`go test -race -cover`, 115 tests across 13 packages incl. new `internal/alert`, `internal/alert/notify`, `internal/anomaly`). Ran a real server end-to-end with both `features.alerts` and `features.ml` on: pushed real Snappy+protobuf remote-write samples, confirmed a threshold rule fires/resolves correctly and an `anomaly`-condition rule fires once the ensemble has trained and a genuine outlier arrives; confirmed `/api/v1/anomalies` correctly ranks the series; took Playwright screenshots (light + dark) of the live dashboard showing both new panels rendering real data. One real debugging detour during this verification, worth recording: an early smoke test pushed samples 100-200ms apart and saw zero anomalies detected — traced to `internal/storage`'s existing (pre-v0.4.0) second-granularity write-dedup guard in `series.write()`, which silently drops any point whose `t.Unix()` doesn't strictly increase from the last stored point, so sub-second-interval pushes were mostly discarded before they ever reached the anomaly detector. Not a v0.4.0 bug — a pre-existing storage-engine granularity constraint that a normal ≥1s scrape/push interval never hits — but worth knowing if testing this feature again with synthetic high-frequency data.
